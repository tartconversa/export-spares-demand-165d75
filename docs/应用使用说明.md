# 备件保障分析应用使用说明

本应用在合成业务资料上区分**故障发生、客户报修、实际领件、履约结果**四个
事件层，预测有解释的故障与备件需求区间，并在预算内选优可落实的保障方案。
评价对象是“设备能否按服务承诺恢复”，不是库存排行榜。

## 1. 运行方式

隔离模式（`-I`，推荐，避免工作目录植入模块）下直接运行包入口：

```bash
python3 -I spares/__main__.py --data data --sims 500 <命令> [参数]
```

非隔离模式也可用 `PYTHONPATH=. python3 -m spares ...`。全局参数
`--cutoff`（默认 `2025-04-21T08:00:00+08:00`，资料第 110 日、在途批次
最早到日）、`--state`（演练状态目录）、`--sims`（蒙特卡洛次数）。

| 命令 | 作用 |
| --- | --- |
| `forecast` | 截点后 90 天故障与备件需求区间、积压、遮挡清单、账面消耗 vs 真实需求 |
| `risk <站>` | 某站风险逐单下钻：来源设备、服务时限、最早可用供给交期 |
| `eta` | 在途批次应用情景迟延后的到达区间（不按最早日确定入账） |
| `plan` | 预算内四种动作（常规/加急/改港/互借）贪心选优与履约评估 |
| `commit` | 把选定动作落实为采购/互借承诺，校验库存、两端扣减并持久化 |
| `simulate-actuals` | 生成演练用后续实际资料（新故障/批次延期/返修验收） |
| `replay` | 用实际资料回看原预测，三分归因并保留原快照 |
| `report` | 输出单文件离线 HTML 演练报告（内联 SVG，无脚本无外链） |

## 2. 完整季度演练

```bash
STATE=drill_state
python3 -I spares/__main__.py --data data --sims 500 --state $STATE forecast
python3 -I spares/__main__.py --data data --sims 500 --state $STATE plan --scenario normal
python3 -I spares/__main__.py --data data --state $STATE commit
python3 -I spares/__main__.py --data data simulate-actuals --out $STATE/actuals --horizon 45
python3 -I spares/__main__.py --data data --state $STATE replay \
    --actuals $STATE/actuals --review-at 2025-06-05T08:00:00+08:00
python3 -I spares/__main__.py --data data --sims 500 report --out drill.html
```

情景通过 `--scenario {normal,port_hold,slow_start}` 选择，对应 plans.csv
中的区域共同迟延、需求倍数与全网总预算（预算是每情景一份，不是每站各一份）。

## 3. 关键口径（与 docs/资料口径.md 对齐）

- **账面消耗 ≠ 故障需求**：缺货时段没有领用不代表没有故障。S2 的 P1 在
  2025-03-23 耗尽并有登记缺货，6 个 G2 工单零领用；全网络 19 个 waiting
  工单均无领用。`forecast` 的“账面消耗 vs 真实故障需求”表量化这一偏差。
- **返修退回不取消需求**：9 个 P1 返修验收回库，但原工单真实消耗了配套 P4，
  需求行保留；回库只增加未来可保障库存。
- **替代与配套**：G1 用 P2（high 资质站可以 P3 替代，basic 站不可）；
  G2 必须 main(P1) 与 aux(P4) 同时到齐才有修复价值。P5 在兼容表中无需求，
  是死库存，应用不会为其规划。
- **在途不确定**：批次给的是 [earliest, latest] 区间，应用在区间内按显式
  均匀假设抽样，`eta` 命令可查；改港产生 redirect_cost 并使该批次只能
  到达一个目的站。
- **时点可知性**：所有估计只读取 `point_in_time(cutoff)` 切片——工单按
  `available_at`、库存/领用按 `occurred_at` 过滤；waiting 工单的
  `repair_at` 为空，绝不参与估计，不能拿后来修复结果预测过去。

## 4. 预测模型与可信度

- 故障率按**设备龄期分桶**（0-30/31-45/46-60/61-75/76+ 天）拟合，
  资料显示风险率随龄期显著上升；代际×环境单元用经验贝叶斯向全网同桶
  收缩，小样本（新站）自动向总体靠拢。
- 资料中每台设备至多 1 次故障，预测按伯努利过程（窗内至多故障一次，
  概率 1−exp(−λ)），不人为制造重复故障。
- 新站的装机计划来自 plans.csv：窗内均匀投运、代际构成同本站在保设备，
  这是情景规则而非观测事实，已在假设登记中标注。
- 输出给均值、P25/P75 与 P05/P95 区间，不用单点确定数；所有资料未直接
  支持的假设（泊松/伯努利过程、均匀到达、互借运输时长、加急对迟延的
  减半敏感度等）在各命令输出的“假设登记”中逐条列出，供用户检查替换。

## 5. 方案选优与承诺纪律

- 优化器以**单位资金带来的加权按时恢复改善**贪心选动作，后果权重
  consequence 高的服务承诺优先；waiting 工单始终计入需求，无法靠拒收
  困难工单美化履约率。
- 全局可行性约束：同一 shipment 最多改港一次；同一出借站×物料累计外借
  不超过其可保障存量。`commit` 会再次校验，库存不足的互借写入
  `rejected_commitments.json`，不占实物。
- 互借承诺立即从出借站可保障库存扣减，借入站在 ETA 前不入账；采购在
  到货入库前不增加现存库存，只记资金占用。未确认的建议永不进台账。

## 6. 回看归因

`replay` 对每个站×物料的缺口给出且仅给出一个类别：

- `demand_error`：实际需求落在按经过时长折算的预测区间之外（泊松波动
  按 √t 缩放，而非线性缩放分位数）；
- `compat_judgement`：需求在区间内，但工单已超服务时限、物料有库存却
  零领用，指向固件/资质/配套判断；
- `fulfillment_change`：需求与兼容判断成立，供给时刻/数量偏离（批次延期、
  承诺未达、无库存）。

原方案的预测以 `plan_snapshot.json` 冻结保留，重预测另存
`replay_snapshot.json`，差异即下一轮预测的学习信号。

## 7. 测试

```bash
python3 -I -m unittest discover -s tests -p "test_business.py" -v
python3 -m compileall -q spares tests
```

27 个业务测试覆盖时点防泄漏、遮挡识别、配套/资质约束、龄期风险率、
区间有序性、承诺两端扣减、改港互斥、预算合规与归因互斥。
原有 `test_sources` 依赖 catalog.json 中声明的文件哈希；当前仓库内
data/ 的实际哈希与声明不一致（提交时即如此，非本应用改动），
该检查会报“资料摘要不一致”，与业务分析代码无关。
